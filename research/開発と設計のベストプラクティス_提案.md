## 案1：「合図」の仕組み（イベント）◎

**ベストプラクティス**：ゲーム開発でよく使う「オブザーバー（観察者）」の形。本体は節目で合図を出すだけ、各機能は聞きたい合図に登録するだけにする（参考：Robert Nystrom『Game Programming Patterns』Observer / Event Queue の章 https://gameprogrammingpatterns.com/observer.html）。

**いまの困りごと**：包み直しが8重になると、
- どの順で動くかが order.json の並び順で決まり、並べ替えると壊れる。
- 1つが前の関数を呼び忘れると、それより前の機能が全部止まる（気づきにくい）。
- 本線の担当ファイルに触らずに済ませるための工夫だったので、それ自体は正しい判断でした。それを決まった形にします。

**やること**
1. 小さなファイル `js/00b_hooks.js` を1つ足す（20行ほど）。
   ```js
   const LT={_h:{},on(n,f){(this._h[n]=this._h[n]||[]).push(f)},
     emit(n,...a){for(const f of this._h[n]||[]){try{f(...a)}catch(e){console.error('[LT]',n,e)}}}};
   ```
2. 本体の節目に1行ずつ合図を足す：`handStart` `handEnd` `action` `render` `sceneStart` `talkAdvance`（本線の担当ファイルに1行ずつ）。
3. **新しいレーンは包み直し禁止、合図に登録する**（並行作業の分担.md に1行足す）。
4. 今ある包み直しは、そのファイルを触る機会に1つずつ移す。一度に全部はやらない。

**効果**：順番に左右されない、1つの機能のエラーが他を止めない（try/catch）、どこで何が動くか `grep "LT.on('handStart'"` で一覧できる。

## 案2：書き方の自動チェック ◎

**ベストプラクティス**：組み立てのたびに機械で間違いを拾う（ESLint などの「静的解析」）。人の目より早く、毎回同じ基準で見られる。

**やること**
- build.py の最後に、組み立てたスクリプトへ `node --check`（文法）と ESLint をかける。設定は今回試したもの（dev/tools/eslint.config.mjs に置く）。
  - 止めるもの：文法の間違い、定義されていない名前、二重定義、**辞書の重複キー**。
  - 知らせるだけ：使っていない変数など。
- 今ある英語訳の重複53組（うち訳違い21組）を1回で片づける（どちらを残すか機械的に並べて、本線か英語担当が選ぶ）。
- GitHub 側の検査（CI）に足すかどうかは「CIの見直し」スレッドに渡す。

**効果**：1ファイルの書き間違いでゲーム全体が真っ白になる事故を、公開前ではなく組み立てた瞬間に止める。今は 0件の「未定義の名前」を 0件のまま保てる。

## 案3：名前と説明をそろえる ◎

**ベストプラクティス**：ファイル名は「いつ作ったか」ではなく「何をするか」で付ける。説明書き（README）は実物と一緒に直す。

**やること**（本線が版と版の間に1回だけ）
- 改名の例：`30b_v63.js` → `30b_pro_fixes.js`（プロ目線の改善）、`32_v63_tail.js` → `32_final_duel.js` など。中身を見て決める。番号のかぶりもずらす。

- README.md のファイル数、並行作業の分担.md のファイル名を実物に合わせる。

## 案4：保存の読み書きを1か所に ◎

**ベストプラクティス**：保存データには版番号を持たせ、古い形は読み込むときに新しい形へ直す（データベースの「マイグレーション」と同じ考え）。公開後は、遊んでいる人の端末に古い保存が必ず残るので、**公開前に入れておくのが一番安い**。

**やること**
- 16_save_ads.js に `saveGet(key, 初期値)` / `saveSet(key, 値)` を足す。中で `{v:版, data:…}` の形にし、`MIGRATE[key][版]` があれば順に当てる。壊れた保存は初期値に戻し、元の文字列は `key+'-broken'` に1つだけ残す。
- 新しいコードはこれだけを使う。今ある直接の `localStorage` 呼び出しは、触る機会に移す。
- qa の save チェック（前の版の保存を新しい版で開く）はそのまま使える。

## 案5：配る札の乱数に種（シード）を ○

**ベストプラクティス**：乱数を種から作ると、同じ種で同じ配りを再現できる。不具合の再現、テストのぶれを減らす、決まった配り（配り札固定）の実装にも使える。

**やること**
- 19_deck_eval.js の `shuffle` だけを種つき乱数に替える（ポットで使っている式と同じ形、数行）。
- 種はハンドごとに記録し、その他画面か不具合報告に「ハンド番号」として出せるようにする。URL に `?seed=123` を付けると同じ配りで始まる（テスト用）。
- CPU の判断などの `Math.random` はそのまま（遊びの手触りは変えない）。第1〜3章の難しさも変わらない（配りの偏りは変わらないため。winrate チェックで確かめる）。

## 案11：Web版のエラー記録 ◎
**ベストプラクティス**：不具合は「起きた時の記録」があると直す時間が大きく減る。サーバーを持たなくても、端末の中に記録しておけば報告に貼ってもらえる。
**やること**：Web版の `reportError` で、エラーの文と場所・版・章・ハンド番号（案5の種）を端末に最大20件ためる（新しい保存キー `shisho-errlog`、案4の形で）。その他画面の「不具合を報告」で、それをコピーしてGitHubの報告フォームへ貼れるようにする。外へは何も送らないので、プライバシーポリシーの変更は要らない。

## 案12：更新のお知らせ ◎
**ベストプラクティス**：PWA は新しい版を見つけたら、遊んでいる人に知らせて、区切りのいいところで読み込み直す（Chrome の公式ガイド「Service worker の更新」の基本形）。
**やること**：新しい版が待っていたら、タイトル画面か章の合間にだけ「新しい版があります（読み込み直す）」を出す。**ハンドの途中では出さない**。sw.js 側の対応はテストサイトのリポジトリの担当（GitHub Pages のスレッド）と合わせる。

## 案13：不具合の重さと公開の基準 ◎
**ベストプラクティス**：ゲーム開発では「バグの重さの段階」と「出してよい基準（バグバー）」を先に決める。迷う時間が減り、公開の判断がぶれない。
**やること**：
- 重い：進めなくなる・保存が消える・チップの計算が合わない・真っ白になる → **1件でもあれば出さない**
- 中：見た目の崩れで操作はできる・訳の抜け → 公開前に直す。間に合わなければ数を決めて残す
- 軽い：言い回し・小さなずれ → 公開後でよい
GitHub の報告フォームと known.json に、この3段階を付ける。

**いま**：控えはすべて同じフォルダの中です。フォルダに何かあると、ソースも調査資料も一緒になくなります。

**ベストプラクティス**：かんばん方式の「同時に進める作業の数に上限（WIPリミット）を置く」。並べる数を減らした方が、ぶつかりと待ちが減って、結局早く出る。
**やること**：本線＋レーン3本までにする。4本目は、どれかが書き戻してから始める。並行作業の分担.md に1行足し、まとめ役が守る。

## 案17：遊ぶ人向けの「更新内容」△
**やること**：版ごとに1〜3行（日本語・英語）を、その他画面と案12のお知らせに出す。テスターが「どこが変わったか」分かるので感想が具体的になる。ストアの「新機能」欄にもそのまま使える。

## 案18：振り返りメモ △
**やること**：公開した版に重い不具合（案13）が出たら、「何が起きた・なぜ・どう直した・次から何を変える」を5行で `dev/振り返り.md` に残す。人を責めず仕組みを直す書き方にする（Google SRE の「非難しない振り返り」）。今日の「古い写しで src を上書きした」件は、すでにこの形に近い記録が並行作業の分担.md にあります。
