## 案1　検査の結果を上書きしないようにする（共有フォルダ）　**おすすめ**

- 何も付けずに回したときの置き場所を、`qa/reports/_runs/<日時>_<ファイル名>/` にする。毎回別のフォルダなので、だれが何回回しても重ならない。
- 版の正式な結果（`reports/v63/`）に書くのは、`--official` を付けたときだけ。これは本線だけが使う（並行作業の分担.md に書く）。
- 同じ版の `--official` が2つ同時に走ったら、後のほうを止める（印のファイルで見る）。
- 基準（baseline.json）を書き直すのも `--official --update-baseline` のときだけにする。今は「基準が無いと勝手に作る」ので、消えたときにレーンの試作で基準ができてしまう。
- `_runs/` は1日たったら消す（容量を食わないように）。

ほかの選び方：レーンごとに `--out` を必ず付ける決まりにする → 付け忘れで同じ事故が起きるので、仕組みで止める上の形がよい。

- 作業：1時間ほど／担当：このスレッド（qa/run_all.js と qa/README.md、並行作業の分担.md に1行）
- 確かめ方：レーンの形で2つ同時に回して、reports/v63/ が変わらないこと。`--official` を2つ同時に回して、後が止まること。
- 1.0 に入れるか：入れる（今日2回起きている）。

## 案2　GitHub の検査を共有フォルダと同じにする　**おすすめ**

- qa.yml の組に、足りない6つを入れる：`text,ftue,script,a11y,perf` ／ `ui,uiux` ／ `fuzz` ／ `rules,basics` ／ `winrate`（save は前の版の控えが GitHub に無いので、今まで通り自動で飛ばす）。
- 組の一覧を手書きしない：`node qa/run_all.js --list` で検査の一覧を出し、どの組にも入っていない検査があれば QA を ❌ にする。これで、検査を足したのに GitHub で回っていない、が二度と起きない。
- 実行機を `ubuntu-24.04` に固定する（D の対策。基準を作った環境と同じにしておく）。Ubuntu 26 に移るときは、基準を作り直す PR を1本出して移る。
- qa.yml に `permissions: contents: read` を足す（読むだけで足りる）。
- 作業：30分ほど＋検査1回／担当：このスレッド（リポジトリへの PR。ゲームの中身は変えない）
- 確かめ方：PR で全部の組が回って ✅、一覧の照合で抜けが0。
- 1.0 に入れるか：入れる（公開前の ✅ が本当に全部の検査を通った意味になる）。

## 案3　勝率の検査をぶれなく・速くする　**おすすめ**

- 1回ごとの乱数を固定する（8回のうち i 回目はいつも同じ配り方）。同じ版なら何度回しても同じ勝率になるので、基準と違えば「本当に変わった」と言える。乱数を固定する仕組みは画面チェック用に既にある（qa/lib/harness.js の seed）。
- 章ごとに別の組にして同時に回す（第1〜4章 → 4組）。12〜18分 → 5分ほどの見込み。
- 1回の上限を短くする（60分 → 20分）。止まったときに早く分かる。
- 乱数を変えると勝率の値も変わるので、入れるときに v62 で基準を1回作り直す（第1〜3章の難しさは v62 のままを基準にする）。
- 作業：1〜2時間／担当：このスレッド（qa/checks/winrate.js、qa.yml）
- 確かめ方：同じファイルで2回回して勝率が1回も違わないこと、v62 で取った基準で v62 が ✅ になること。
- 1.0 に入れるか：入れる。**今の v63 の止まり（C）は、案3を待たずに本線が確かめる必要があります**（第1章 90%→50% は、ぶれにしては大きい）。

## 案4　速くする（1.0 の後）

- Playwright の公式の入れ物（コンテナ）で動かして、毎回の入れ直しを省く。字体は入れ物に足す。
- package-lock.json を作って `npm ci` にする（部品の版がいつも同じになる）。
- 作業：1時間ほど。効果は1回あたり数分。

## 案5　守りと決まりを固める（1.0 の後）

- 外の部品（actions/checkout など）を名札ではなく、中身の番号（コミットの SHA）で指定する。Dependabot がこの番号も月1回更新する。GitHub や安全の専門家がすすめている形。
- 「QA のまとめ」という、どの PR でも必ず回る小さな検査を1つ足す（index.html が変わらない PR では、すぐ ✅ で終わる）。これでルールセットに「QA のまとめが ✅ 必須」を付けられる（G の対策）。付けるのは satou さんの操作（Settings → Rules）。
- main への push で QA をもう1回回すのをやめる（PR で回したものと同じなので）。

## 入れた結果（2026-10-10、案1＋2＋3 に決定）

- 案1：入れた（qa/run_all.js）。ふだんの結果は `qa/reports/_runs/`、`reports/v<版>/` と基準は `--official`（本線だけ）。2つ同時に回して reports/v63・v64 が変わらないこと、`--official` の二重起動が止まることを確かめた。
- 案3：入れた（qa/checks/winrate.js、`--ch`）。v62 で第1・2章を2回回し、8回とも1回ずつ同じ勝ち負けになった（WWWWWWWW／LLLWLLWL）。
  - わかったこと：乱数を固定しても、版が変わると配り方の並びが変わる（ゲームが乱数を使う回数が変わるため）。なので「同じファイルの回し直しでぶれない」は直ったが、「前の版と比べる」は今も8回の抜き取り。必要なら、GitHub で章ごとに分けて空いた時間で回数を16回に増やす（1.0 の後でもよい）。
  - 手元の v63（乱数固定）：第1章 88%（7/8）、第2章 25%、第3章 50%、第4章 63%。第1〜3章は基準の幅に入っている。GitHub の v63 で出た「第1章 50%」は、乱数を固定していない回のぶれの可能性が高い。
- 案2：PR #8（.github/workflows/qa.yml だけ）で入れた。9組すべて ✅（約16分）、2026-10-11 00:25Z に自動マージ。実行機 ubuntu-24.04 固定、権限は読むだけ、どの組にも入っていない検査があると「検査の一覧」が ❌。
- 追加（16:20、本線の調べより）：第2章の「時間切れ」は止まったのではなく、長いゲーム（60〜80ハンド）が4つのブラウザでコアを分け合って240秒を超えたもの。1回の上限を「手数×8秒」にし、手が進んでいるのに時間切れなら「決着なし」（負け扱い、games に D）、本当に止まったとき（20秒動かない）だけエラーにした。GitHub の組の上限は40分（PR #8）。v63 第2章で時間切れ0、335秒。
  - 注意：v63 第2章は、この回 LWLLLLLL、前の回 LWWLLLLL で1回だけ違った。乱数を固定しても、時間のかかり方で結果が変わる回がまだある（ゲームの中に時刻を使う所がある可能性）。同じ版の回し直しのぶれは大きく減ったが、ゼロではない。
