# CI（自動の検査）の高速化 提案

2026-10-17 作成（satou さんの依頼「CIの実行が遅いです。カイゼン提案してください」）。
対象：satou-aaaaa/last-tell の QA（.github/workflows/qa.yml）と、共有フォルダの検査 qa/。

**おすすめ：案1＋案2＋案3（検査の網はそのまま、または今より細かくなる）。**
案4 は手順の変更で、網は最後には同じ。案5・案6 は網を弱めるか費用がかかるので、おすすめしない。

---

## 測ったこと（10-15〜10-17 の QA の実行、GitHub の記録から）

### 1回の時間
| 種類 | 1回の時間 | いちばん遅い組 |
|---|---|---|
| 公開のPR（publish-…、長い版） | **22〜30分**（平均 約25分） | fuzz 16〜29分、rules,basics 約21分、winrate 第2・4・6章 15〜19分 |
| ふつうのPR（短い版） | 14〜17分 | rules,basics 約14分 |

- 準備（Playwright・字体を入れる）は 20〜60秒で、遅さの原因ではない。待ち行列もほぼ無い（どの組も0.3分以内に始まる）。
- **時間はほぼ全部「検査を回す」そのもの**。全体の長さは、いちばん遅い組（fuzz と rules,basics）で決まる。

### 遅い組の中身
| 組 | 中身 | 遅い理由 |
|---|---|---|
| rules,basics | rules（17の対戦を4つずつ、1つ最大200秒）＋ S2 の直接測定 ＋ basics | 17対戦が1つの組に入っている。4つずつ「全部終わるまで待つ」ので、遅い1つに合わせて残りが待つ |
| fuzz（長い版） | 31のモードを4つずつ、1モード50ハンド・最大420秒 | 31モードが1つの組。時間切れ（420秒）まで回るモードがあると、その4つ組全体が待つ。だから16〜29分とばらつく |
| winrate 第2・4・6章 | 1章24回（第4章からは読む・読まないの対で48回） | 1章が1つの組 |

### いちばん時間を食っているのは「やり直し」
v0.89.1（今日）は、**1つの版で QA を7回**回している（06:59〜12:19、合計 約2時間20分。まだ通っていない）。
落ちた理由の多くは、ゲームの壊れではなく、**回数が少なくて揺れる割合の検査**：

| 落ちた理由 | 回数 | 例 |
|---|---|---|
| S2（リバーの2倍ベットへのコール率） | 4回 | クロウ 17%（6回）→50%（8回）→46%（13回）→56%（9回）と、回ごとに大きく揺れる |
| 第6章の読み比べ（tellgap） | 1回 | 読まない25%／読む0%（各24回） |
| 正しく見つけたもの | 2回 | 新しい台詞に「夜」、S2 の下限（直接測定 クロウ 3%） |

1回25分の検査を「数字が揺れたから」まるごと回し直すのが、待ち時間のいちばん大きな原因。

---

## 案

### 案1 組を細かく分ける（網はそのまま）【おすすめ】
- rules を3つの組に分ける（17対戦を6・6・5に）、basics を別の組にする
- fuzz（長い版の Chromium）を3つの組に分ける（31モードを約10ずつ）
- winrate 第2・4・6章を2つずつに分ける（前半12回・後半12回。札の種は今と同じ）
- 短い組はまとめる（unit＋公開サイト＋text… を1つ、winrate 第7・11・13・15章を1つ）。GitHub の無料枠は**同時20組まで**なので、組の数は20以下に保つ
- 結果は「検査のまとめ」が今までどおり1つにまとめるので、読み方（qa/ci_result.sh）は変わらない

**見込み：公開のPR 25分 → 約10〜12分、ふつうのPR 15分 → 約7〜8分。** 検査の中身・回数・合否の基準は変えない。

### 案2 「4つずつ待つ」をやめて、空いたらすぐ次を回す（網はそのまま）【おすすめ】
rules・fuzz・winrate は今、4つ（winrate は3つ）ずつ「全部終わるまで待ってから次の4つ」。
1つが終わったらすぐ次を始める形に変える（同時に回す数は今と同じ）。
**見込み：各組が 15〜25% ほど短くなる。** 案1 と合わせるとさらに効く。中身・回数は変わらない。

### 案3 揺れる割合の検査は、境目のとき自動で回数を足す（網はむしろ強くなる）【おすすめ】
S2・読み比べなどの割合は、合格の線の近くで回数が少ないと「たまたま」落ちる。今はそのたびに25分の検査を全部やり直している。
- 合格の線から外れたが回数が少ない（例：20回未満）ときは、その検査の中で**同じやり方で回数を足して測り直し**、足した後の数字で決める
- 足しても外れていれば ❌（今と同じ）。はっきり外れている（回数が十分）ときはすぐ ❌
- 足したことは結果に書く（「13回→33回で判定」）

**見込み：今日のような「同じ版で何度もやり直し」がほぼなくなる。1つの版が通るまでの時間は、今日の約2時間20分 → 1〜2回分（20〜25分）。** 回数は今より増えるので、見逃しは減る。

### 案4 公開のブランチでも、直しの途中は短い版、最後だけ長い版（網は最後には同じ）
今は publish-… のブランチに押すたびに長い版（25分）が回る。直しの途中は短い版（案1後は約7分）で回し、マージの前に長い版を1回回す（下書きを外したとき、またはラベル「長い版」）。
自動マージは長い版が ✅ のときだけにするので、公開される版の検査は今と同じ。
ただし、途中の版では第5〜15章の勝率などが測られないので、**途中で気づくのが遅れることはある**。

### 案5 第5〜15章の勝率と WebKit を毎晩に回す（⚠️ 網を弱める・おすすめしない）
公開のPRでは第1〜4章の勝率と Chromium だけを回し、残りは毎晩 main で回して Issue にする。
**PRの時点では検査が減る**ので、悪い版が一度公開されてから気づくことがある。案1〜3 で十分速くなる見込みなので、おすすめしない。

### 案6 大きい実行機（8コア以上）を使う（費用がかかる・おすすめしない）
公開リポジトリでも、大きい実行機は**有料**（分単位の料金）。今の4コアの実行機は無料。案1〜3 で足りる見込みなので、おすすめしない。

---

## おすすめを選んだときの進め方
1. 案2（空いたらすぐ次）と案3（回数を足す）を qa/ に入れる（共有フォルダの qa/ が正本。本線の次の公開で repo に写る、または qa/ だけの PR）
2. 案1 の組分けを qa.yml に入れ、rules・fuzz・winrate に「何番目の組か」を渡す口（`--part 1/3` など）を足す
3. 1つの PR で前後の時間を比べ、結果（合格・警告の数）が今と同じことを確かめてからマージする

## 結果（2026-10-17、PR #69 でマージ済み）
- satou さんが 案1＋2＋3 を選び、入れた。共有フォルダの qa/ にも同じ変更を当てた。
- 長い版：一番遅い組 約13分（前は 21〜29分）。短い版：約9分（前は 14〜17分）。他の PR と重なると、無料枠の同時20組を分け合うので待ち時間が増える。
