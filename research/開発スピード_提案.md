## 2. 分かったこと

1. **一番の詰まりは「本線がひとりで全部を作る」こと。** 同じ本線でも、レーンが作って渡した v62 は約20分で出て、自分で作った v63 は3時間を超えています。
2. **入ってくる量が、出せる量より多い。** 1時間に6件の 1.0 の作業が増え、本線は1つの版に3時間以上かかっています。今のままでは列が伸び続けます。
3. **検査が1回 約37分で、版の途中で何度も回している。** v63 では作業ごとに「検査中」が出ています。半分は勝率の検査で、これは CPU や章の中身を変えたときしか意味がありません。
4. **版が大きいと、1つの不具合で全部が待つ。** v63 は10件を重ねてから全体の検査をしているので、どれか1つで止まると全部が出ません。
5. 新しく決まった仕様の多くは**新しいファイル**（21b・21c・06b・07b）で作る形になっていて、レーンで分けやすい状態です。

## 3. 案

### 案1　決まった仕様は、提案を作ったスレッドがそのままレーンで作る【おすすめ・効果が一番大きい】
- 仕様を書いたスレッドが、`lane.py` で src/ の写しを取り、自分の担当ファイルだけを作って、検査と3画面の確認まで済ませて書き戻します。本線は order.json に1行足して、全体の検査を回して公開するだけにします（v62 と同じ形）。
- 今の列だと、次のように分けられます（同じファイルを大きく触るものは同じ担当にまとめる）。

| 担当 | 作業 | 主に触るファイル |
|---|---|---|
| 本線 | UI案3、所持チップ案1〜3、顔にかぶるチップの直し（v64） | 27_render, 28_controls, 01_style, 21_dealer_fx |
| レーンA | チェック案1〜3、フォールド案1〜3（手の絵とルールを共有するので1つに） | 21b_check_knock（新）, 21c_fold_muck（新）, 22_sound |
| レーンB | 相手の名前 案2＋3 | 06b_names（新）, 27_render に少し |
| レーンC | 話しかける 案1＋2 | 07b_talk_hear（新）, 28_controls に少し |
| レーンD | ライブ感の総点検（仕様が届いたら、触るファイルを見て決める） | — |

- 見た目の CSS はレーンごとの `01b_style_<レーン>.css` に書くので、01_style.css でぶつかりません。27_render・28_controls を少しずつ触る分は、lane.py の3方向の取り込みで合わせます（ぶつかったら止まるので、壊れたまま入ることはありません）。
- よい点：v62 の例では、本線の作業が3時間 → 20分ほどになっています。列の5件がほぼ同時に進みます。
- 弱い点：同時に動くスレッドが増えるので、利用上限に早く当たります（今日も1回当たっています）。上限は全部のスレッドで共有なので、**速くなるのは「待ち時間」の部分で、作業の総量は変わりません**。

### 案2　検査を「変えた所に合わせて」回し、全部は公開の前に1回だけにする【おすすめ・すぐできる】
- 作業の途中では、変えたファイルに関係する検査だけを回します。全部（約37分）は、版を出す前に1回だけ回します。

| 変えたもの | 回す検査 |
|---|---|
| 見た目だけ（CSS、描画、ボタン） | ui, uiux, a11y（約3〜4分） |
| セリフ・英語 | text, script, fuzz の英語だけ |
| 新しい保存キー | save |
| ポーカーの進め方・ルール | basics, rules, fuzz |
| CPU・章の中身・配り札 | winrate（第1〜3章を守る検査。これだけで約15分） |

- `run_all.js` に「前の版から変わったファイルを見て、回す検査を選ぶ」オプション（例：`--changed`）を足すだけで、仕組みは今のままです。
- よい点：v63 のように作業ごとに検査を回す場合、1回あたり 約37分 → 3〜10分ほどになります（推定）。勝率の検査を飛ばすのは、CPU・章・配り札のファイルに触れていないときだけです。
- 弱い点：思わぬ所に影響する変更を途中で見逃すことがあります。ただし公開の前には必ず全部を回すので、外には出ません。

### 案3　版を小さくして、できた順に出す【おすすめ】
- 「10件を重ねて1つの版」ではなく、「1〜3件ずつ、できたものから版にする」にします。案1でレーンが別々に仕上がるので、それぞれを次の版に乗せていきます。
- 公開の回数は増えますが、GitHub 側は検査が通れば自動で取り込み・公開まで進むので、手間はほとんど増えません。テスターが毎回違う版を触る問題は、テスト公開の日だけ版を固定すれば避けられます。
- よい点：1件の不具合で他の全部が止まらない。satouさんがテストサイトで新しいものを見られるのが早くなる。
- 弱い点：版の数字が早く進みます（v63, v64, v65…）。

### 案4　1.0 に入れる新しい仕様の受け付けを、いったん止める
- [1.0の範囲.md](../dev/1.0の範囲.md) では「新しい提案は基本は公開後」と決めていますが、今日は選ばれた提案がそのまま 1.0 に入っています。
- 1.0 の列が片付くまで、新しい提案（毎日の改善提案を含む）は**「公開後」の列にだけ入れる**ようにします。提案そのものは続けます。1.0 に入れたいものは、satouさんが「1.0 に」と言ったものだけにします。
- よい点：列が伸びなくなり、公開日が見えるようになる。
- 弱い点：小さくてよい案も 1.0 には入らなくなります。

### 案5　すでに 1.0 に入っているものを、いくつか公開後に回す
- 今日の午後に入った6件のうち、遊びの芯（ストーリー・ポーカーの正しさ）に関わらない見た目の演出を公開後に回すと、列が短くなります。
- 例：チェック・フォールドの見せ方、相手の名前の見せ方、ライブ感の総点検の一部。
- よい点：1.0 が一番早く出ます。
- 弱い点：satouさんが選んだものを後に回すことになります。どれを回すかは satouさんに決めてもらいます。

## 4. おすすめ

**案1＋案2＋案3** をおすすめします。どれもゲームの中身は変えず、進め方だけを変えます。案1が一番効きますが、案2と案3がないと、レーンが速く作っても本線の検査と大きな版で詰まります。

列が伸び続ける問題も直したい場合は、**案4** も足すのがよいと考えます。案5は、1.0 の公開日を一番早くしたいときの選択肢です。

始める順番：
1. 案2（検査の絞り込み）を足す。本線の作業には触れずに、qa/ のほうで足せます。
2. v63 が出たところで、案1のレーンA〜C を始める。本線は v64（UI案3＋所持チップ）を続ける。
3. 案3：レーンの作業ができたものから順に版にする。
