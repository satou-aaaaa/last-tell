# LAST TELL 変更後の検査（qa/）

ゲーム（story/shisho.html）を変えたら、毎回これを回します。2026-10-10 satou さんが「案1＋案2」を選んだもの。

## まず：重い検査は GitHub（CI）で回す（2026-10-14 satou「できるだけCI上で実行し、Claude のトークンを消費しない形で」）

Claude のスレッドは、勝率・画面の撮影・全部の検査を**自分の作業場所で回さない**。GitHub で回して、結果を読むだけにする。

| いつ | どうする | 結果の読み方 |
|---|---|---|
| 作業の途中・書き戻す前（レーン、修正のスレッド） | `sh qa/ci_check.sh <作った.html> <名前>` → 下書きのプルリクエストができる（マージも公開もされない） | `subscribe_pr_activity` でその PR を見張り、CI が終わった知らせが来たら `sh qa/ci_result.sh <番号>` |
| 版を出すとき（本線） | 今までどおり `publish-v<版>` ブランチでプルリクエスト。**publish- のブランチは自動で長い版**（第5〜15章の勝率、前の版3つのセーブの引き継ぎ、120ハンドの重さ） | 同上。`--save v<版>` で共有フォルダの `qa/reports/v<版>/` に写す（版の正式な結果） |
| 版ごとのレビュー（クリエイター・UI/UX・交代） | 自分では回さない | `sh qa/ci_result.sh v<版> --shots`（一覧3枚と、前の版から変わった画面だけが落ちる） |

- 結果はブランチ `qa-results` の `pr/<番号>/` と `v<版>/` にある：`summary.md`（まずこれ。❌・⚠️・勝率・変わった画面）、`report.md`（全部）、`baseline_候補.json`、`ui/_一覧_縦.jpg`・`_一覧_横.jpg`・`_一覧_PC.jpg`（12場面を1枚に）、`ui/changes.json`（前の公開版と比べて見た目が3%より多く変わった画面）。
- 画面の確認（毎回の決めごと）は、まず一覧3枚を見て、変わった画面だけ1枚ずつ見る。変わっていない画面は見直さなくてよい。
- 待つときに `sleep` や繰り返しの確認をしない（それ自体がトークンを使う）。CI の終わりは PR の知らせで来る。
- 基準（baseline.json）の書き直し：公開した版の `baseline_候補.json` を `qa/baseline.json` に写す（本線だけ、satou さんの OK のあと。今までの `--official --update-baseline` の代わり）。
- 手元で回してよいのは、ブラウザを使わない数秒の検査だけ：`node qa/unit/run.js`、`node qa/run_all.js X.html --only unit`。CI が使えないとき（GitHub が落ちている等）だけ、下の「回し方」で手元で回す。
- 仕組み：.github/workflows/qa.yml の「検査のまとめ」ジョブ、qa/tools/ci_summary.js・ci_shots.js。Actions の成果物（qa-report-*）は Claude の環境から落とせないので、qa-results ブランチに置いている。

## 回し方（手元。CI が使えないときだけ）

```
sh /mnt/project-files/qa/run_all.sh                      # 短い版（毎回の変更で）。結果は reports/_runs/ の新しいフォルダ
sh /mnt/project-files/qa/run_all.sh --full               # 長い版（テスト公開・ストア提出の前）
sh /mnt/project-files/qa/run_all.sh 別のファイル.html     # ファイルを指定
node /mnt/project-files/qa/run_all.js --only fuzz,ui     # 一部だけ（text, ftue, fuzz, rules, winrate, ui, uiux）
node /mnt/project-files/qa/run_all.js 作った.html --changed v62 [--src 作業場所/src]
                                                         # 変えた所だけ（作業の途中で。控え v62 と比べて検査を選ぶ）
node /mnt/project-files/qa/run_all.js --only winrate --ch 1,2   # 勝率を章を選んで
sh /mnt/project-files/qa/run_all.sh --official [--full]   # 版の正式な結果（本線だけ）→ reports/v<版>/
node /mnt/project-files/qa/run_all.js --list              # 検査の一覧
node /mnt/project-files/qa/unit/run.js [作った.html|src]   # ルールの単体テストだけ（ブラウザなし、数秒）
```

- **結果の置き場所（2026-10-10 CIの見直し 案1）**：ふだんは `qa/reports/_runs/<日時>_<ファイル名>_<版>_<番号>/` に、毎回別のフォルダで書く。だれが何回回しても重ならない。1日たったら次に回したときに消える。最後に「結果の置き場所:」と出る。
  - `qa/reports/v<版>/` と `baseline.json` に書くのは `--official` のときだけ。**本線だけが使う**（`--only`・`--changed`・`--ch`・`--out` とは一緒に使えない）。同じ版の `--official` が同時に2つ走ると、後のほうは止まる。
  - 今日（2026-10-10）レーンの試作の検査が reports/v63/ を2回上書きしたため。
- **勝率の乱数は固定**（案3）：i 回目はいつも同じ配り方。同じファイルなら何度回しても同じ勝率になるので、基準と違えば本当に変わった。result.json の `games`（W/L の並び）で1回ずつ比べられる。

- `--changed`（2026-10-10 開発スピード 案2）：変わった src のファイルから回す検査を選ぶ（qa/lib/changed.js の表）。見た目だけなら ui・uiux と安い検査で数分。勝率（約15分）は CPU・章・配り札（02・10・14・15・25）を変えたときだけ。どの検査に関わるか決めていないファイルがあれば全部回す。結果は `reports/v<版>_changed/`、基準は書き換えない。**版を出す前は必ず `--changed` なしで全部を回す。**
- 結果は `report.md`（画面の画像は `ui/`）。不合格があると終了コード 1。
- 必要なもの：Node と Playwright（クラウドの作業環境には入っている。GitHub では自動で入れる）。

## ルールの単体テスト（qa/unit/、2026-10-14）

ポーカーのルールの計算（役の判定、ポットの分け方、最低レイズ、ブラインドの席）は、画面を通さずに直接確かめます。

- ゲーム側：ルールの計算は `src/js/19_deck_eval.js` と `src/js/19b_rules.js`（`Rules.*`）に置き、画面や S・CFG に触らない。ゲームの act・showdown・startHand などはそれを呼ぶだけ。
- 検査側：`qa/unit/load.js` が、組み立てたファイル（または src）から `// @unit-begin 名前`〜`// @unit-end 名前` の間だけを取り出して Node の空の箱で動かす。GitHub でも index.html だけで回る。
- テストを足すとき：`qa/unit/tests/` のどれかに場面を足す（ルールの種類ごとのファイル）。ルールの計算を新しく書くときは 19b_rules.js に入れる（画面のコードを入れると、箱の中でエラーになって分かる）。
- ブラウザで打ちながら見る検査（basics・rules・fuzz）は、ゲームが決まりを正しく呼んでいるか・CPU の打ち方の数字を見るために残す。

## GitHub（テスト公開）での自動実行

テスト公開のリポジトリ satou-aaaaa/last-tell の `.github/workflows/qa.yml` が、index.html か qa/ が変わったプルリクエストとプッシュのたびに回します。検査は組に分けて同時に回し、実行機は ubuntu-24.04 に固定しています。**新しい検査を足したら qa.yml の組（QA_GROUPS）にも足す**（入れ忘れると「検査の一覧」が ❌ になる）。
- 短い版：ふつうのプルリクエスト（ci_check.sh の下書きも）。長い版：`publish-…` ブランチと、Actions → QA → Run workflow で「長い版」を選んだとき。
- 組の分け方（CIの高速化 案1・2・3、2026-10-17）：rules（S1・A2／A1／S2）と fuzz は3つ、勝率は全部の章の対戦を長い版10組・短い版4組に順に配る（`run_all.js --part k/n`）。勝率の判定は「検査のまとめ」が組の生の結果を混ぜてから qa/lib/winrate_judge.js で行うので、結果は分ける前と同じ。各検査の中も「1つ終わったらすぐ次」（qa/lib/pool.js）。A1 の割合が合格の線の近く（回数が20未満か、差が標準誤差の2倍以内）で外れたときは、同じ打ち方をもう一回り足してから決める。S2 の直接の測り方（S2-direct）も同じ条件で200回ずつ足す（結果に「境目だったので…」と出る）。S2 の打って数える方は ⚠️ だけで、合否は S2-direct で決める（satou 2026-10-17「直接測定で判断」）。GitHub の無料枠は同時20組なので、組を足すときは数に気をつける。
- 最後の「検査のまとめ」が全部の組の結果を1つにして qa-results に置き、❌・⚠️ を注釈に、要約をジョブのまとめに出す。結果の無い組（時間切れなど）も ❌ になる。
- セーブの引き継ぎは、CI では main の index.html（長い版は前の版のタグ2つも）を前の版として使う（`QA_PREV_HTML`）。
- 全部の PR で回る（2026-10-14 案7）。index.html も qa/ も qa.yml も変わっていない PR は、重い組を飛ばして「検査のまとめ」だけ ✅ になる。ルールセットで「検査のまとめ」を必須にできる。自動マージは index.html か qa/ を変える PR だけ（.github/ を変える PR は手で）。
- ぶれ対策（案1）：rules・basics・fuzz・ftue の「続きから」も乱数を場面ごとに固定。コール率などの割合は、外れたキャラが20回以上測れていなければ ⚠️。
- iPhone の Safari（案3）：WebKit で ui・fuzz を回す組。画面の新しい問題は ⚠️（字の幅が違うため）、止まる・エラーは ❌。画像は `ui/WebKit_*.jpg`・`ui/_一覧_WebKit_縦.jpg` ほか。
- 画面（案2）：前の公開版から変わった画面は `ui/_比べ_<場面>.jpg`（前｜今｜違う所）。新しく足した場面は、基準（baseline.json の uiScenes）に入るまで ⚠️。
- 部品の版は qa/package-lock.json と Actions の SHA で固定（案7）。Playwright を上げるときは package.json と package-lock.json の両方。
- 毎晩（案5）：.github/workflows/playthrough.yml が main で「通しで遊ぶ」を回し、結果を qa-results の `nightly/` に置く（`sh qa/ci_result.sh nightly`）。❌ なら Issue「通しで遊ぶ検査が ❌」。
- 人が見るとき：プルリクエストの Checks →「検査のまとめ」の Summary。画像は qa-results ブランチの `pr/<番号>/ui/` か、Actions の成果物 qa-report-*（PNG）。
