# 開発の効率化の提案（2026-10-10）

毎回の自動検証（[qa/毎回の検証を効率化する提案.md](../qa/毎回の検証を効率化する提案.md)）は別のスレッドで作っているので、ここでは**それ以外**をまとめます。

## いまの進め方で時間がかかっている所

| いまのやり方 | 困っていること |
|---|---|
| ゲームは1枚のファイル（`story/shisho.html`、約850KB・6,500行。1行で19万字の行もある） | どこを直すにも全体を読み込む必要があり、変更が遅く、壊しやすい |
| 変更は「文字列を探して置き換える」スクリプトを順番に当てる（`story/patch*.py`） | 前のスクリプトの結果が前提なので、**順番にしか進められない**。（訂正：patch38・42・43 はもともと無く、全パッチは story/patches/ に順番つきで揃っている） |
| 版ごとにファイルを丸ごと複製（`shisho-v53`〜`v60`で約5.6MB） | 「どこが変わったか」が分からない。戻すのも手作業 |
| ゲームを直すのは1つのスレッドだけ。仕様が10件以上、列に並んでいる | 音楽と掛け合いのように**関係ない作業も待たされる** |
| 提案スレッドは 提案.md＋見本.html＋動画＋実装仕様.md を作り、ゲーム担当が仕様を読んでコードに書き直す | 同じ内容を2回書いている。仕様とコードのずれも出る |
| テストサイトの更新は、別スレッドが手でビルドして push し、まとめ役が伝言する | 公開のたびに手間と伝言が挟まる |

## 案

### 案1　ゲームをいくつかのファイルに分けて、組み立てで1枚にする【おすすめ・効果が一番大きい】
- 見た目（CSS）、ポーカーの仕組み、CPUの考え方、キャラ、章ごとのストーリー、掛け合いの台詞、英語訳、音、をそれぞれ別のファイルに分けます。
- `build.py` が全部をつないで、**今と同じ1枚の `shisho.html`** を作ります。テストサイト・アプリ版・アーティファクトの作り方は変わりません。
- 最初に「分けて組み立て直したものが今の v60 と1文字も違わない」ことを確かめてから切り替えるので、ゲームの中身は変わりません。
- よい点：直したい所のファイルだけ開けばよい。置き換えスクリプトの順番待ちがなくなる。案3の並行作業ができるようになる。
- 弱い点：切り替えに1回まとまった作業が要り、その間ゲーム担当の作業を一度止めます。

### 案2　ソースを非公開のGitHubリポジトリで管理する【おすすめ・案1とセット】
- 案1で分けたファイルを非公開のリポジトリに入れ、変更は1件ずつ「ブランチ → 自動検証 → 取り込み」で進めます。
- 版の丸ごと複製と置き換えスクリプトの連鎖は不要になります。差分がそのまま記録になり、どの版にもすぐ戻せます。
- 今の `last-tell` は公開リポジトリなので、ソース（ストーリーのネタバレを含む）は**別の非公開リポジトリ**に置くのがよいと考えます。
- **satouさんにお願いしたいこと：非公開リポジトリを1つ作ってよいか**（名前の案：`last-tell-src`）。作るのはこちらでできますが、外に作るものなので確認を取ります。

### 案3　関係ない作業を並行で進める（案1・2の後）
- いまの列（掛け合い → プロ目線の修正 → プロポーカー目線の修正 → あの日の回想 → 音楽 → 第4弾 → 主人公）は、触る場所がほとんど重なりません。
  - 例：音楽は「音」のファイル、掛け合いは「台詞」のファイル、CPU修正は「CPUの考え方」のファイル。
- 2〜3のスレッドに分けて同時に進め、取り込みは1つずつ（毎回の自動検証を通ったものだけ）にします。第1〜3章の難易度を変えないルールは自動検証で守ります。
- よい点：列の長さがおよそ半分〜3分の1になる。
- 弱い点：同じ場所を触る作業（例：プロ目線とプロポーカー目線の修正は両方CPU）は同じスレッドにまとめる必要があります。

### 案4　仕様書を「そのまま入れられる形」にする【すぐできる】
- 掛け合いの台詞（`research/キャラ同士の掛け合い_台詞.js`）は、データがそのままゲームに入る形でした。これを全部の提案に広げます。
- 仕様書のひな形を決めます：①触るファイル ②保存キー ③台詞データ（日本語と英語を並べたファイル） ④「できた」の条件（自動検証にそのまま足せる形で書く）。
- よい点：ゲーム担当が仕様を読み直して書き直す手間と、訳し漏れが減る。
- 弱い点：提案スレッドの作業は少し増える。

### 案5　提案の作り方を軽くする【すぐできる】
- 動画は、動きが大事な提案（演出・カメラなど）だけにします。
- 提案の段階では「案の比較＋見本」だけを作り、実装仕様書は**satouさんが選んだ後に、選ばれた案の分だけ**作ります。
- よい点：選ばれなかった案の仕様を書く時間がなくなる。

### 案6　テストサイトの公開を自動にする（案2の後）
- 非公開リポジトリの本線に取り込まれ、自動検証に通ったら、`last-tell` へ自動で公開します。
- 公開のたびに「この版で変わったこと」の一覧も自動で作ります。
- 公開の頻度は「取り込むたび」ではなく、**1日1〜2回まとめて**がよいと考えます（テスターが毎回違う版を触らないように）。

### 案7　スキルと「開発の入口」を作る【すぐできる】
- 新しいスレッドが毎回、ファイルの場所・ルール（「夜」を使わない、お金の話をしない、第1〜3章は変えない、3画面の確認など）を調べ直しています。
- 共有フォルダの一番上に `README.md`（開発の入口：どこに何があるか、守るルール、作り方の手順）を置きます。
- 「ゲームを直すときの手順」を1つのスキル（`last-tell-dev`）にします。既にある `last-tell-release-check`・`last-tell-proposal-demo` と並べます。
- よい点：スレッドの立ち上がりが早くなり、ルールの抜けが減る。

## おすすめの進め方

1. **すぐ**：案4・案5・案7（ゲーム本体に触らないので、今の列を止めずにできる）
2. **掛け合い（v61）が終わった区切りで**：案1＋案2に切り替え（v60/v61と1文字も違わないことを確かめてから）
3. **その後**：案3で並行作業を始め、案6で公開を自動にする

satouさんに決めてもらいたいのは次の2つです。
- この進め方でよいか
- 非公開リポジトリ（`last-tell-src`）を作ってよいか

## 効率化以外のアイディア（2026-10-10 追加）

### A　「1.0で出すもの」を決めて、残りは公開後の更新に回す【おすすめ】
- やりたいことの列は増え続けていて、公開日が決まりません。第一部＋第二部と今決まっている修正を「1.0」とし、第4弾の要素・第三部などは公開後の更新（1〜2週ごと）に回すのがよいと考えます。
- 早く出すほど、本物の遊んだ人の反応で次に作るものを決められます。

### B　ゲームの中に「感想を送る」ボタンを置く
- 「その他」画面から、短いフォーム（例：Googleフォーム）を開きます。どの章・どの画面からかを自動で添えます。
- 観察テストの人集めを待たずに、テストサイトを触った人の声が集まります。ゲーム側で記録や追跡はしません。

### C　読み込みを軽くする
- いまのゲームは約850KBで、版ごとに大きくなっています。組み立て（案1）のときに圧縮し、第二部などの後半のデータは必要になってから読む形にすると、スマホでの最初の表示が速くなります。

### D　satouさんの「判断待ち」を1か所にまとめる
- いまは判断が各スレッドに散らばっています。判断待ちの一覧（何を・どのスレッドで・おすすめはどれか）を1つのページにまとめ、まとめ役が更新します。戻ってきたときに一度で片付けられます。
