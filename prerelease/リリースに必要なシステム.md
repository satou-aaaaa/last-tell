# リリースに必要なシステム（一覧）

前提：1ファイルのHTML（`story/shisho.html`）を Capacitor で包み、App Store と Google Play に出す。EU も配信する。広告は AdMob、計測は Firebase、機種変更は引き継ぎコード。サーバーは持たない。
作成日：2026-10-08。[モバイルアプリ化調査.md](../mobile/モバイルアプリ化調査.md) と [リリース前調査.md](リリース前調査.md) に書いたことは繰り返さず、**まだ書かれていなかった「仕組み」の部分**をまとめた。

## 結論

**自前のサーバーやデータベースは要らない。** 必要なのは次の7つで、どれも無料か、すでに予定している費用の範囲で揃う。

| # | 必要なもの | 何のため | 状態 |
|---|---|---|---|
| 1 | コードの置き場所（GitHub など） | 履歴を残す、ビルドを自動化する | **未着手・新規** |
| 2 | ビルドと署名の仕組み | ストアに出せるアプリを作る。署名の鍵をなくすと更新できなくなる | **未着手・新規** |
| 3 | 小さな公式サイト（自分のドメイン） | プライバシーポリシー、サポート窓口、`app-ads.txt` | 既存調査で決定済み |
| 4 | Firebase（Analytics＋Crashlytics＋Remote Config） | 離脱の分析、**落ちたときの検知**、**古い版への更新のお願い** | Analytics のみ既存。他2つは新規 |
| 5 | 同意の仕組み（UMP＋ATT）と Firebase への反映 | EU の同意を広告と計測の両方に効かせる | 広告側は既存。**計測側への反映が新規** |
| 6 | セーブデータの仕組み（形式の版番号、移し替え、引き継ぎコード） | 更新や機種変更でセーブを壊さない | 方針は既存。**版番号と形式が新規** |
| 7 | アプリとしての基本動作（裏に回ったら音を止める等） | 審査落ちや低評価を防ぐ | **一部新規** |

**逆に、要らないもの**（サーバーがないので最初から不要）：ログイン、アカウント削除機能（ストアの必須要件はアカウントを作れるアプリだけ）、リワード広告のサーバー検証、課金のレシート検証、ランキングのサーバー。将来ランキングやクラウドセーブを足すときに初めて検討すればよい。

## 1. コードの置き場所

- GitHub の非公開リポジトリを1つ作り、HTML・Capacitor の設定・アイコンなどをまとめて入れる。無料で使える。
- いまは1ファイルの HTML だが、アプリ化では Vite などのプロジェクトにして、**HTML（ゲーム本体）と、広告・保存・計測を呼ぶ薄い部分を分ける**。Web版とアプリ版で同じゲーム本体を使い回せる。
- 入れてはいけないもの：署名の鍵、そのパスワード（2章）。

## 2. ビルドと署名の仕組み

ストアに出すアプリには「誰が作ったか」を示す電子署名が必要。**一番大事なのは鍵の保管**。

| | Android | iOS |
|---|---|---|
| 必要な鍵 | アップロード鍵（keystore ファイル）。Play App Signing に登録すると、配布用の本当の鍵は Google が預かる | 配布用の証明書と、プロビジョニングプロファイル（Apple Developer で作る） |
| なくした場合 | アップロード鍵は Play Console で再登録を申請できる（Play App Signing を使っている前提） | 作り直せる。ただし期限切れ（証明書は1年）に注意 |
| ビルド場所 | 自分の PC（Windows でも可） | Mac が必要。なければ Codemagic や GitHub Actions の macOS でクラウドビルド |

- **Play App Signing は必ず使う**（新規アプリでは標準）。自分の鍵だけで管理すると、なくした時点でそのアプリを更新できなくなる。
- 鍵とパスワードはパスワード管理アプリと別の場所の両方にバックアップし、クラウドビルドを使うならその「シークレット」設定にだけ入れる。
- **版番号のルールを決めておく。** 表示用（例 1.2.0）と、毎回1ずつ増やす内部番号（Android の `versionCode`、iOS の build 番号）の2つがあり、内部番号が前より大きくないと提出できない。
- 自動化（任意）：GitHub に push したら Android の AAB と iOS のビルドを作り、Play の内部テストと TestFlight に上げる。最初は手作業で十分で、提出が月に何度もあるようになってからで良い。

### リリースの流れ（ストア側の仕組み）
- Android：内部テスト → クローズドテスト（12人×14日、既存調査どおり）→ 本番。**本番は「段階的公開」で 10%→50%→100% と広げる**と、問題が出たときに止められる。
- iOS：TestFlight → 審査 → 公開。**「段階的リリース」**（7日かけて自動更新を広げる）を使える。
- Web の中身をストアを通さずに差し替える「ライブ更新」の仕組みもあるが、Apple は審査を通らない機能変更を禁じているので、最初は**すべてストア経由で更新**する前提にする。

## 3. 公式サイト

既存調査で決まっている内容（ポリシー、サポート、`app-ads.txt`）を置く場所。仕組みとして必要なのは次の3つだけ。

- **独自ドメイン**（年1,000〜2,000円程度、推測）。`app-ads.txt` はストアに登録した「開発者のWebサイト」のドメイン直下に置く必要があるので、ドメインは途中で変えない前提で選ぶ。
- **無料の静的ホスティング**（GitHub Pages、Cloudflare Pages など）。Web版のゲームも同じ場所に置ける。
- **サポート用メールアドレス**。ストアに公開されるので、個人のメインアドレスとは分ける（独自ドメインのアドレスか、専用の Gmail）。

## 4. Firebase（計測・クラッシュ検知・遠隔設定）

1つの Firebase プロジェクトに iOS と Android のアプリを登録し、設定ファイル（`GoogleService-Info.plist` / `google-services.json`）をアプリに入れる。以下はすべて無料枠で足りる見込み（推測）。

### 4-1. Analytics（既存調査どおり）
章ごとの離脱を見る。イベント案は [リリース前調査.md](リリース前調査.md#5-1-分析どの章で離脱するか) を参照。

### 4-2. Crashlytics（新規、おすすめ）
- アプリが落ちたときに、どの機種・どの版で落ちたかを自動で集める。
- **注意：ゲームは WebView の中の JavaScript で動いているので、JS のエラーでは「アプリが落ちた」扱いにならず、自動では集まらない。** HTML 側で `window.onerror` と `unhandledrejection` を受けて、Crashlytics のプラグイン（`@capacitor-firebase/crashlytics`）に「エラーが起きた」と送る処理を足す。
- 入れたら、プライバシーポリシーとストア申告に「クラッシュデータ・診断データ」を足す。

### 4-3. Remote Config（新規、あると安心）
サーバーなしで、アプリの外から一部の値を変えられる仕組み。
- **強制アップデート**：「この版より古い人には更新のお願いを出す」最低版番号を置いておく。致命的なバグを出したときに、古い版の人を新しい版へ誘導できる。Android は Google Play の「アプリ内アップデート」で、アプリ内からそのまま更新させることもできる。
- **広告の頻度**：インタースティシャルを何ハンドに1回出すか、などを後から調整できる。
- **お知らせ**：メンテナンスや新章の告知を1行出す。
- 取得できないとき（オフラインなど）は、アプリに入れておいた既定値で動くようにする。

### 4-4. 入れないもの
Firebase Authentication、Firestore、Cloud Functions など「サーバー側」の機能は今は使わない。使うと、ポリシー・ストア申告・アカウント削除などの追加対応が必要になる。

## 5. 同意の仕組みを計測にも効かせる

既存調査では、広告の同意（UMP＋ATT）までを決めた。**Firebase も EU では同意の対象**なので、同じ同意結果を計測にも渡す必要がある。

1. 起動時に UMP で同意を確認し、iOS は続けて ATT を出す（既存調査の手順どおり）。
2. **Firebase Analytics は、同意が取れるまで「同意モード」で拒否の状態から始める。** UMP の結果を見て `analytics_storage`・`ad_storage`・`ad_user_data`・`ad_personalization` の4つを許可／拒否に設定する（Google の同意モード v2）。
3. iOS で ATT が拒否されたら、Analytics に広告IDを集めさせない設定にする。
4. 設定画面の「プライバシー設定」ボタンで同意をやり直したら、その結果を Firebase にも反映し直す。

この処理は「広告まわりの薄いラッパー」（[収益化調査.md](../monetization/収益化調査.md) の方針）と同じ場所に置くと、Web版とアプリ版で切り替えやすい。

## 6. セーブデータの仕組み

`shisho.html` を確認したところ（変更はしていない）、セーブは `shisho-progress`（クリアした章）、`shisho-settings`（設定）、`shisho-notes`（メモ）の3つのキーに保存していて、**中身に版番号がない**。アプリとして長く更新するなら、次を最初の版から入れておく。

- **版番号を付ける**：例 `{ "v": 1, "cleared": 3, ... }`。将来セーブの形を変えたとき、古い形を新しい形に変換する処理（移し替え）を書けるようにするため。版番号がないと、どれが古い形か判別できない。
- **保存先の移し替え**：初回起動時に `localStorage` の内容を `@capacitor/preferences` に写す（既存調査の方針）。Web版のセーブは別のアプリ扱いなので、アプリには引き継がれない点に注意（Web版から来た人には引き継ぎコードで移してもらう）。
- **引き継ぎコードの形式**（案）：
  1. 3つのキーをまとめた JSON（版番号付き）を作る
  2. 圧縮して、URL でも安全な英数字（Base64URL）にする
  3. 先頭に形式の版、末尾に短いチェック用の数字を付ける。入力ミスをその場で見つけられる
  4. 表示画面に「コピー」ボタン。入力画面は貼り付けに対応する
  - 1人用でランキングもないので、改ざんを厳しく防ぐ必要はない。チェック用の数字は「打ち間違いの検出」が目的。
  - iPhone⇔Android でも、Web版⇔アプリでも同じコードで移せる。
- **端末バックアップ**：Android は自動バックアップ、iOS は iCloud バックアップで Preferences の中身が引き継がれる（同じOS間のみ）。Capacitor の初期設定でバックアップは有効になっている見込み（推測。ビルド時に `allowBackup` を確認）。

## 7. アプリとしての基本動作

ブラウザでは気にしなくてよかったが、アプリでは必要になるもの。`shisho.html` には今、画面が裏に回ったときの処理がない。

| 動作 | 内容 | 使うもの |
|---|---|---|
| 裏に回ったら音を止める | ホームに戻った・電話が来たときに BGM・効果音を止め、戻ったら再開。止めないと低評価や審査指摘の原因になる | `@capacitor/app` の状態変化、または `visibilitychange` |
| 広告中は音を止める | インタースティシャル・リワード広告の表示中はゲームの音を止め、閉じたら戻す | AdMob プラグインのイベント |
| Android の戻るボタン | 画面ごとに「前の画面へ」「終了確認」を決める。何も決めないとアプリがいきなり閉じる | `@capacitor/app` の backButton |
| 起動画面とアイコン | 各サイズの画像を1枚の元画像から作る | `@capacitor/assets`、`@capacitor/splash-screen` |
| 画面の向き・ノッチ | 縦固定、セーフエリア対応（既存調査で記載） | ネイティブ設定、CSS の `env(safe-area-inset-*)` |
| フォントの同梱 | ネット読み込みをやめる（既存調査で記載） | — |

## 8. 公開後に見る場所

新しく作るものはないが、公開後に見る画面を決めておく。

- **Play Console の Android Vitals**：クラッシュ率・ANR（応答なし）率。一定を超えるとストアでの表示が下がる。
- **Play Console の「リリース前レポート」**：クローズドテストに上げると、Google が実機で自動起動して不具合を報告してくれる（無料）。
- **App Store Connect／Xcode のクラッシュ情報**と、Firebase Crashlytics。
- **レビューへの返信**：両ストアとも返信できる。サポート窓口と合わせて対応する。

## 作る順番（既存の「進め方」に組み込む場合）

1. GitHub に置き、Vite＋Capacitor のプロジェクトにする（1章）
2. セーブに版番号を付け、Preferences への移し替えと引き継ぎコードを作る（6章）
3. 裏に回ったときの音・戻るボタンなどの基本動作（7章）
4. Firebase（Analytics、Crashlytics、Remote Config）を入れる（4章）
5. AdMob と同意の仕組みを入れ、同意結果を Firebase にも渡す（5章）
6. Android の鍵を作って Play App Signing に登録し、内部テスト → クローズドテスト（2章）
7. 公式サイトとドメインを用意し、ポリシーに Crashlytics の分も書き足す（3章）
8. iOS の証明書を作り、TestFlight → 審査（2章）
